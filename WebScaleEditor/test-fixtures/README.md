# Reference Fixtures from the Stock Max Scale Editor

This directory holds reference `scale.txt` files generated by the **stock Max-based ScaleEditor** (the one shipped with the module, in `../../ScaleEditor/`). We use them to verify that our web editor's parser and serializer produce output that is bit-for-bit (or at minimum semantically) identical to what the canonical tool produces.

Once these files are populated, the test runner (`node --test ../tests.js`) will:

1. Parse each fixture and assert its slot structure (catches parser regressions against real-world input).
2. Re-serialize and byte-compare against the original (catches serializer divergence from Max's output, modulo known/documented differences).

We also plan to ship a small CLI helper `tools/diff-scale.js` for ad-hoc semantic diffs of any two `scale.txt` files going forward.

---

## How to generate the fixtures

You'll need a Mac with the `ScaleEditor.app` build (the macOS `.app` from `../../ScaleEditor/` — does not require Max 9).

For each fixture below:

1. Launch the editor (clean state if possible — quit and relaunch is fine between fixtures).
2. Follow the click-by-click instructions.
3. Save to the filename shown (the editor's Save dialog can write directly into this folder, or you can save anywhere and `mv` it).
4. If you can, also drop the bytes through `od -c` and paste the tail of the output — useful for confirming line endings and trailing characters.

Order doesn't matter, but fixture 1 is the most diagnostically valuable single file (it tells us how Max terminates files), so consider doing it first.

## Fixture 1 — `01-empty-fresh-save.scale.txt`

**Goal:** Capture Max's exact byte format for an empty/default file.

**Steps:**

1. Open the editor with no file loaded, OR load any file and click "Clear" for all 16 banks until every slot has zero notes.
2. Do NOT touch the LED colors — leave them at whatever defaults the editor uses (likely all zeros).
3. Click Save.

**What this fixture tests:**

- The exact "empty state" line format. Does Max write `0 0 0 0 0 0 0` (seven zeros) per line? Or fewer? Or with different separators?
- **Trailing-newline behavior.** The shipped factory file (`../../factoryPreset/scale.txt`) has no trailing newline on the last line but does have a trailing space. We need to know whether Max always writes files this way, or whether the factory file was hand-generated with a different tool.

**Also do (one-time only):**

```bash
od -c 01-empty-fresh-save.scale.txt | tail -3
```

Paste the output into the commit message or share it back. It tells us LF vs CRLF, presence of trailing space / newline, and any unusual byte sequences.

## Fixture 2 — `02-led-extremes.scale.txt`

**Goal:** Confirm LED channel range and boundaries.

**Steps:**

1. Start from an empty editor (or build on top of fixture 1).
2. Go to **Bank 0** (slot 0).
3. LED 1: set R=255, G=255, B=255 (pure white).
4. LED 2: set R=0, G=0, B=0 (pure black).
5. No notes selected on the piano. Root Emphasize OFF.
6. Leave all other slots empty.
7. Save.

**What this fixture tests:**

- Whether Max actually accepts 255 in the RGB fields, or silently clamps to a lower value (e.g., 127). We currently assume the range is 0–255 based on the screenshot evidence — a saved file confirms it.
- That `(0,0,0)` and `(255,255,255)` both round-trip cleanly through Max.

## Fixture 3 — `03-simple-triad.scale.txt`

**Goal:** Verify a clean small scale with Root Emphasize OFF and non-extreme LED values.

**Steps:**

1. Empty editor.
2. Bank 0.
3. Piano: click notes for semitones **0**, **4**, **7** (a C major triad in the lowest octave). All other notes off.
4. LED 1: R=200, G=50, B=100.
5. LED 2: R=50, G=200, B=100.
6. Root Emphasize OFF.
7. Other slots empty. Save.

**What this fixture tests:**

- Note ordering for a few notes in a single octave.
- Non-extreme LED values (not all zeros, not all max). Confirms the RGB field ordering in the file matches what we assume (`R G B R G B` for LED1 then LED2).
- That `rootEmphasize=false` is encoded as `0` and not something else.

## Fixture 4 — `04-rootemph-major.scale.txt`

**Goal:** Replicate factory slot 0 exactly via the Max editor today.

**Steps:**

1. Empty editor.
2. Bank 0.
3. Piano: click semitones **0** and **7** in the lowest octave, then **12, 14, 16, 17, 19, 21, 23** in the next octave (i.e., a C major scale with Root Emphasize semantics — same notes as factory slot 0 / Major(R)).
4. LED 1: R=127, G=0, B=0.
5. LED 2: R=127, G=0, B=51.
6. **Root Emphasize ON.**
7. Other slots empty. Save.

**What this fixture tests:**

- This is intentionally identical content to the factory file's slot 0. If the Max editor today writes this slot byte-for-byte identical to `factoryPreset/scale.txt` line 1, we've confirmed Max's output is stable and matches the shipped factory file. If not, the factory file was likely generated by some older tool or script and Max now writes a slightly different format — important to know.
- Confirms `rootEmphasize=true` is encoded as `1`.

## Fixture 5 — `05-many-notes-out-of-order.scale.txt`

**Goal:** Test note ordering and deduplication.

**Steps:**

1. Empty editor.
2. Bank 0.
3. Piano: click notes in this exact order: **23, 0, 12, 7, 1, 14, 22**. (Out of order — do not pre-sort in your head.)
4. *Optional, if you want to test dedup:* click semitone 7 a second time. If the editor toggles it OFF, ignore (it does what ours does). If it stays ON, that's a dedup pass — interesting data point.
5. LED colors: whatever you like. Root Emphasize OFF.
6. Other slots empty. Save.

**What this fixture tests:**

- Does the Max editor write the notes in the order they were clicked, or sorted ascending? Our serializer sorts ascending — if Max preserves click order, our output will byte-differ even though the scales are semantically identical. Critical to know before any byte-level diff test could pass.

---

## Fixture 6 (bonus, optional) — `06-notes-only-upper-octave.scale.txt`

**Goal:** Verify behavior when no notes exist in the lowest octave.

**Steps:**

1. Empty editor.
2. Bank 0.
3. Piano: click ONLY semitones **12, 14, 16** (in the second octave). No notes in the lowest octave.
4. LED colors: any.
5. **Root Emphasize OFF.**
6. Other slots empty. Save.

**What this fixture tests:**

- What happens when there are no octave-0 notes. The ghost-extrapolation feature in our web editor assumes the firmware extrapolates upward from the highest-defined octave. This fixture lets us confirm whether the Max editor permits this shape of scale and how it serializes it.
- Whether Max forces a note in octave 0 (some editors auto-add the root). If it doesn't, our model holds.

## Once the fixtures are in place

Send word (or just commit them and notify) and I'll:

1. Add a test block to `../tests.js` that parses each fixture and asserts the expected slot structure.
2. Add a byte-comparison test that serializes the parsed result and diffs against the source file (with explicit handling for any known/documented differences such as trailing newline).
3. Write `../tools/diff-scale.js` so you can run `node ../tools/diff-scale.js fileA.scale.txt fileB.scale.txt` to do ad-hoc semantic comparisons.

The `tests.js` block will dynamically discover any `*.scale.txt` file in this folder, so you can add more fixtures later without re-editing the test code.
